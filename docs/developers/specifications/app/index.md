# Part 1: Operational & Design Specification

## 1. Component Overview

* **Purpose:** This component serves as the **Bootstrapper** and **Entry Point** for the `app-manager` CLI application. Its primary responsibility is to initialize the runtime environment, register available commands, and determine the execution mode (Headless vs. Interactive) based on user input.
* **Role in System:** **Orchestrator**. It bridges the gap between the Node.js runtime (`process`) and the application's core logic. It sits at the top of the call stack.

## 2. Architecture & Patterns

* **Design Patterns:**
* **Singleton/Module Pattern:** Imports instantiated services (`logger`, `configService`, `commandRegistry`) directly, treating modules as singletons.
* **Command Pattern:** Registers specific command classes (`CommitCommand`, etc.) into a central commandRegistry.
* **Strategy Pattern (Implicit):** dynamically selects the execution strategy (`runHeadless` vs. `runInteractive`) based on input arguments.


* **State Management:**
* **Stateless (Internal):** The `index.ts` file itself does not maintain persistent state.
* **State Initializer:** It is responsible for triggering the initialization of stateful services (`logger`, `configService`).


* **Complexity Assessment:** **Low**. The control flow is linear with a single major conditional branch. However, the side effects (global registration) at the top level add implicit complexity to testing.

## 3. Dependency Graph

* **Internal Dependencies:**
* **Services:** `loggerService`, `configService`.
* **Core Systems:** `commandRegistry` (Command Registry).
* **Modes:** `headlessMode`, `interactiveMode`.
* **Commands:** `CommitCommand`, `PushCommand`, `SyncCommand`.


* **External Dependencies:**
* `node:url` (Standard Lib)
* `node:path` (Standard Lib)
* `process` (Global Node Object)


* **Coupling Analysis:** **High/Tight Coupling**.
* The file explicitly imports and registers concrete command implementations (`CommitCommand`, etc.). Adding a new command requires modifying this entry point.
* It relies on concrete imports of services rather than Dependency Injection (DI), making unit testing reliant on module mocking.



#### 4. Data Types & Interfaces

* **Key Interfaces:**
* No local interfaces are defined.
* Relies on string primitives for filesystem paths.


* **Return Types:**
* `main(targetRoot: string, toolRoot: string)`: **`Promise<void>`**
* Top-level execution: **`void`** (implicitly).



#### 5. Functional Logic Specification

**A. Global Side Effects (Module Load Time)**

* **Logic:** Upon importing this file, the `commandRegistry` singleton is immediately populated.
* **Execution:**
1. `commandRegistry.register(new CommitCommand())`
2. `commandRegistry.register(new PushCommand())`
3. `commandRegistry.register(new SyncCommand())`



**B. Method: `main**`

* **Signature:** `export async function main(targetRoot: string, toolRoot: string): Promise<void>`
* **Logic Flow:**
1. **Service Initialization:** Calls `logger.init(targetRoot)` and `configService.init(toolRoot)` to bind services to the context.
2. **Argument Parsing:** Slices `process.argv` starting at index 2 to isolate user arguments.
3. **Mode Dispatch:**
* **If** `args.length > 0`: Await `runHeadless(targetRoot, args)`.
* **Else**: Await `runInteractive(targetRoot)`.




* **Side Effects:**
* Mutates state in `Logger` and `ConfigService`.
* Reads global `process.argv`.


* **Error Handling:**
* No internal `try/catch`. Errors generated by services or modes propagate up to the caller (the Bootstrap section).



**C. Bootstrap Logic (Conditional Execution)**

* **Logic:** Checks `if (process.argv[1] === currentFile)`.
* **Flow:**
1. Calculates `targetRoot` (Current Working Directory).
2. Calculates `toolRoot` (One directory up from the script location).
3. Invokes `main(targetRoot, toolRoot)`.


* **Error Handling:**
* Wraps `main` in a `.catch()` block.
* Logs 'Fatal Error' via `console.error`.
* Forces exit via `process.exit(1)`.

### Part 2: Appendix - Testing Reference

#### 1. Mocking Strategy

To unit test `main` effectively, the following modules must be mocked using a framework like Jest or Sinon. The file has high external coupling.

* **`./services/loggerService`**: Mock `logger.init` (Spy).
* **`./services/configService`**: Mock `configService.init` (Spy).
* **`./commands/commandRegistry`**: Mock `commandRegistry.register`.
* **`./modes/headlessMode`**: Mock `runHeadless` (Spy/Stub).
* **`./modes/interactiveMode`**: Mock `runInteractive` (Spy/Stub).
* **`process.argv`**: This creates a challenge. Since `process.argv` is read directly inside `main`, tests must temporarily modify `process.argv` or the code should be refactored to accept `args` as a parameter to `main`.

**Mock Behavior definitions:**

* `runHeadless`: Should return `Promise.resolve()`.
* `runInteractive`: Should return `Promise.resolve()`.

### Recommendations for Refactoring (Architectural Note)

1. **Dependency Injection:** Do not instantiate `CommitCommand` etc., inside the file. Pass a `CommandLoader` or similar configuration.
2. **Pure Function:** `main` reads `process.argv` directly. It is better to pass `args: string[]` into `main` as an argument. This makes `main` deterministic and easier to test without mutating the global `process` object.
